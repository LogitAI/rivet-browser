# INTENT

이 문서는 Rivet Browser의 결정과 이유를 기록한다. 결정은 소유자가 내린다. 바꾸려면 이 문서를
먼저 바꾸고 SPEC과 구현을 따른다.

## 1. 동기

- 브라우저를 포크한 제품은 Chromium 보안 업데이트와 내부 변경을 계속 따라가야 한다.
- 사용자는 브라우저를 바꾸면 로그인, 패스키, 동기화, 확장 프로그램, 미디어 호환성을 다시 옮겨야 한다.
- Arc류 작업 공간과 AI 에이전트 경험은 원하지만, 새 브라우저에 종속되고 싶지는 않다.
- Ember 사용자는 컴퓨터를 옮기면서 에이전트 작업을 이어 간다. 브라우저도 그 작업의 일부여야 한다.

## 2. 협상 불가 조건

| ID | 조건 | 이유 |
|---|---|---|
| C1 | Rivet은 Chromium 포크나 웹뷰를 만들지 않는다 | 엔진 유지보수와 호환성 이주를 사용자에게 다시 강요하지 않기 위해서다 |
| C2 | 실제 브라우저 프로세스 안에 Rivet 런타임을 직접 통합한다 | 외부 동반 앱만으로는 프레임, 입력, 탭, 에이전트 경험을 충분히 하나로 만들 수 없다 |
| C3 | 구현 언어는 Rust다 | 런타임, CLI, IPC, Windows 통합에 하나의 시스템 언어를 쓴다 |
| C4 | Windows가 첫 호스트다 | 직접 통합의 창 모델과 설치 경로를 한 플랫폼에서 먼저 검증한다 |
| C5 | 에이전트 제어는 CLI의 일급 기능이다 | IDE와 자동화 에이전트가 사람과 같은 브라우저를 쓸 수 있어야 한다 |
| C6 | 표시 여부는 호출자가 고른다 | 브라우저 처리만 필요한 작업에 화면 합성과 캡처 비용을 강제하지 않는다 |
| C7 | 자격증명은 브라우저와 운영체제의 보안 저장소에 남긴다 | Rivet과 Ember가 비밀번호, 패스키, 쿠키를 복사하는 설계는 허용하지 않는다 |
| C8 | Ember는 사용자 설정과 논리 작업 공간의 기준점이다 | 사용자가 컴퓨터를 옮겨도 Rivet 경험을 이어 가야 한다 |

## 3. 핵심 결정

### D1. Rivet은 설치된 브라우저를 호스트로 쓴다

Rivet은 사용자가 설치한 Chrome 또는 호환 Chromium 브라우저를 실행한다. 렌더링, GPU, DRM,
패스키, 확장 프로그램, 브라우저 업데이트는 해당 브라우저가 계속 맡는다. Rivet은 이를 새 엔진으로
대체하지 않는다.

### D2. 직접 통합은 브라우저 자신의 창과 레이아웃 안에서 한다

런처는 브라우저를 app window 모드로 연다. 위쪽 한 줄은 Rivet이 그린다(D12).
브라우저의 탭바와 툴바는 쓰지 않는다. Rivet은 별도 최상위 창을
만들지 않고, 브라우저 창을 다른 창의 자식으로 옮기지 않으며, 전체화면이나 키오스크 모드에 기대지 않는다.

브라우저 프로세스 안의 Rivet 런타임은 두 가지를 한다.

- Chromium 프레임 뷰가 클라이언트 뷰 위치를 정하는 가상 함수 하나를 기록된 빌드에서만 바꾼다. Chromium은
  왼쪽에 사이드바 폭을 비우고 자기 타이틀바, 캡션 버튼, 웹 콘텐츠를 그 옆에 직접 배치한다. 입력, 메뉴,
  IME, 접근성 좌표도 Chromium이 스스로 계산한다.
- 사이드바는 DirectComposition visual로 같은 브라우저 창에 붙이고 Direct2D와 DirectWrite로 그린다.
  Windows가 사이드바와 브라우저를 한 창으로 합성하므로 최소화, 최대화, 스냅, 애니메이션, 그림자가 함께
  움직인다.

이것은 Chromium의 공개 embedding API가 아니다. 지원 빌드를 표로 공개하고 빌드마다 회귀 검증한다(D7).

사이드바 디자인의 기준은 `rivet/runtime/windows/demo/rivet-shell-demo.html`이다. 이 연구의 서체
Newsreader, Manrope, DM Mono는 SIL Open Font License 1.1로 런타임에 내장하고 라이선스를 함께 배포한다.

### D2-기각. 검토하고 버린 통합 방식

| 방식 | 버린 이유 |
|---|---|
| Rivet 호스트 창에 브라우저 창을 자식으로 넣기 | 브라우저 자체 타이틀바와 캡션 버튼이 함께 들어와 버튼이 두 벌이 된다. 지우려면 전체화면이 필요하고 종료 안내가 남는다. 최상위 창을 자식으로 바꾸면 활성화, 포커스, IME가 비정상이 된다 |
| 브라우저 창에 딸린 팝업 사이드바 | 별도 창이라 최소화, 최대화 애니메이션과 위치 조정이 브라우저와 따로 움직인다 |
| non-client 영역을 예약하고 GDI로 그리기 | Chromium 최상위 창은 `WS_EX_NOREDIRECTIONBITMAP`이라 GDI 그림이 보이지 않는다 |
| non-client 영역에 DirectComposition으로 그리기 | 창의 합성 대상은 클라이언트 영역에서 잘린다 |
| GPU 프로세스의 합성 단계 가로채기 | 픽셀만 옮길 수 있고 레이아웃과 입력 좌표는 바뀌지 않는다. 샌드박스, 재시작, 비공개 구조 문제도 있다 |
| 숨긴 브라우저 화면을 캡처해 보여 주기 | 지연, IME 어긋남, DRM 영상 차단이 생기고 디버깅 포트가 필요하다 |
| CEF, WebView2 임베딩 | C1 위반이고 사용자의 실제 브라우저 프로필을 쓰지 못한다 |
| user32 좌표 API 가로채기 | 여러 API의 좌표를 하나하나 보정해야 하는 억지 구현이다 |

### D3. CLI는 브라우저 작업의 공용 표면이다

사람용 프레임과 에이전트용 CLI는 같은 로컬 제어 채널을 사용한다. CLI의 표시 정책은 `visible`,
`hidden`, `auto`다. `hidden`은 보이는 창과 프레임 스트림을 만들지 않지만, 웹 엔진의 렌더러와
JavaScript 실행을 끄지는 않는다.

### D4. Ember는 설정과 작업 공간을 동기화한다

Ember 서버는 사용자별 Rivet 설정 문서와 논리 작업 공간을 저장한다. 클라이언트는 이를 받아 로컬 브라우저
창과 Rivet 프레임에 적용한다. 브라우저 프로필 파일을 서버로 복사하거나 여러 컴퓨터 사이에서 병합하지
않는다. 인증 상태는 각 브라우저의 공식 동기화와 사용자의 로그인으로 유지한다.

### D5. Ember의 컴퓨터 egress를 재사용한다

Ember가 브라우징 egress 컴퓨터를 정하면, Rivet은 그 컴퓨터의 Rivet 호스트에서 실제 요청을 실행한다.
요청의 출발 IP와 로컬 네트워크 접근은 선택된 컴퓨터의 것이어야 한다. Ember의 현행 SOCKS/CDP relay와의
정확한 결합 방식은 PR-3의 설계와 실험으로 결정한다.

### D6. DSA의 설치 도구 흐름을 재사용한다

Rivet은 DSA에서 검증한 WiX 기반 설치, 서명된 업데이트 목록, 설치 검증 흐름을 재사용한다. DSA 전용
서비스, Android 이미지, 커널, 라이선스 목록은 Rivet에 가져오지 않는다. Rivet 설치기는 Rust 바이너리와
Rivet 서비스만 패키징한다.

### D7. 브라우저가 업데이트되어도 Rivet 창은 끊기지 않는다

소유자 결정(2026-10-31): 브라우저 업데이트 뒤 Rivet 창이 일반 브라우저로 열리는 시간은 1분도 허용하지 않는다.
그런 공백이 있으면 쓸 수 없는 제품이다. 이전 결정처럼 새 빌드의 행이 나올 때까지 몇 시간 기다리는 방식은
버린다.

사용자가 쓰는 시스템 브라우저의 업데이트는 막거나 늦추지 않는다. 대신 다음을 겹쳐서 공백을 없앤다.

1. 미리 준비한다. 정기 작업이 Stable 배포 전에 공개되는 빌드와 버전 기록을 지켜보고, 사용자에게 도달하기 전에
   행을 만들어 검증한다.
2. 표를 따로 배포한다. 지원 빌드 표는 서명된 데이터로 내려받아 Rivet을 다시 설치하지 않고 적용한다.
3. 실행 시 다시 찾는다. 표에 없는 빌드는 이전 빌드의 함수 지문으로 주소를 찾고, 모든 검사를 통과할 때만 적용한다.
4. 마지막 안전망으로 검증된 빌드를 보관한다. 앞의 세 가지가 모두 실패하면 Rivet 창은 Rivet이 보관한 마지막
   검증 빌드로 열고, 새 빌드가 지원될 때까지 그 빌드를 쓴다. 이 동안 오래된 빌드를 쓴다는 보안 경고를 보여 준다.

- 런타임은 여전히 검증되지 않은 코드를 덮어쓰지 않는다. 다만 Rivet 런처가 그 상태의 브라우저로 창을 열지 않는다.
- 사용자 컴퓨터에서 PDB를 내려받지 않는다. 추출은 CI가 하고 클라이언트는 표만 받는다.
- 4번은 보안 수정이 늦어지는 대가가 있다. 소유자 결정(2026-10-31): 보관 빌드는 새 빌드를 처음 발견한 때부터 최대 7일 쓴다. 7일이 지나면 보관 빌드로 창을 새로 열지 않고 이유를 알린다. 일반 브라우저 모양으로 대신 열지 않는다.
- 4번은 아직 실현 가능성이 검증되지 않았다. 브라우저 복사본에서 앱 바운드 암호화와 로그인 유지가 동작하는지
  먼저 확인해야 한다. 브라우저 소유 인증 정보는 이 과정에서도 복사하거나 내보내지 않는다.
### D8. 선택할 수 있는 브라우저

런처는 Google Chrome, Microsoft Edge, Brave, Naver Whale, Samsung Internet을 보여 준다. 실행 파일은 각
설치 프로그램이 등록한 App Paths에서 찾고, 설치되지 않은 브라우저는 고를 수 없다. 사이드바 통합은 지원
빌드 표에 있는 빌드에만 적용한다. 공개 심볼이 없는 브라우저의 지원 방식은 열린 질문이다.

소유자 결정(2026-11-02): 브라우저별 기능 차이를 두지 않는다. 지원하는 브라우저는 모든 Rivet 기능이 같게 동작해야
한다. 어떤 기능을 맞추지 못한 브라우저는 그 기능만 빼고 지원하지 않고, 맞출 때까지 지원 브라우저로 부르지 않는다.

소유자 결정(2026-11-02): Rivet은 Chromium에 붙여 쓰는 프레임이다. 위 브라우저 목록과 App Paths 탐색은 이 결정으로
바뀐다.

- 임의의 Chromium 계열 실행 파일을 지정해 쓴다. 특정 브라우저에 맞춘 제품으로 만들지 않는다.
- Chromium 코드만 호출하고 수정한다. 브라우저 회사의 자체 코드는 호출하지 않는다.
- 회사가 화면을 바꿔도 동작하도록 구현하는 것을 목표로 한다. 회사가 바꾼 화면 때문에 Chromium 코드로 동작시킬 수
  없는 브라우저는 포기한다.

소유자 결정(2026-11-02): 브라우저 선택 화면을 없애고 첫 설정 창으로 바꾼다. 첫 설정 창은 지금 Rivet UI와 비슷한
느낌으로 만들고, 자동 감지한 Chromium 계열 브라우저 목록을 보여 주고, 프로필을 정한다. 이 창은 아직 브라우저 창이
없을 때 뜨므로 D11의 예외다. 프로필은 Rivet 전용 프로필이다. 브라우저의 기존 프로필에는 들어가지 않는다.

소유자 결정(2026-11-04): 회사가 바꾼 화면은 app window로 피한다(D12). 모든 기능은 app window와 Chromium 함수만으로
만들고, 브라우저별 코드 경로를 두지 않는다. 주소는 아직 빌드마다 사람이 찾으므로 임의 실행 파일 지원은 주장하지 않는다.

### D9. Rivet 창은 Rivet의 작업 표시줄 정체성을 가진다

브라우저는 자기 창에 자기 AppUserModelID와 아이콘을 붙인다. Rivet은 자기 창에 Rivet의 ID, 다시 실행
정보, 아이콘을 붙여 작업 표시줄에서 브라우저와 따로 묶이게 한다. 시작 메뉴 바로가기도 같은 ID를 가진다.

### D10. 작업 공간과 탭은 Arc, Dia, Crest의 사이드바 모델을 따른다

- 스페이스마다 이름, 색, 기반 브라우저, 프로필을 고를 수 있다. 같은 Rivet 창에서 스페이스를 바꾸면 그
  스페이스의 브라우저와 프로필로 바뀐다.
- 탭 목록은 고정 탭, 폴더, 오늘 탭의 세 층이다. 소유자 결정(2026-11-05): 오늘 탭만 기본 12시간 뒤 보관하고,
  기간은 설정에서 바꾼다. 폴더의 탭과 고정 탭은 보관하지 않는다.
- 링크와 새 창으로 열리는 링크는 현재 스페이스의 새 탭으로 연다. 길게 누르면 링크 미리보기로 연다.
- 소유자 결정(2026-11-05): 링크 규칙은 다른 앱이나 사이트에서 연 링크를 고른 스페이스, 미니 창 또는 현재
  스페이스로 보낸다. 규칙은 호스트나 URL 앞부분으로 맞추고, 위에서부터 처음 맞는 규칙을 쓴다. 맞는 규칙이 없으면
  현재 스페이스의 새 탭으로 연다.
- 탭 닫기와 탐색은 Dia를 따른다. 닫은 탭의 아래 탭이 선택되고 Ctrl+Shift+T로 되살린다.
- 분할 보기, 링크 미리보기, 미니 창, 링크 규칙, 명령 바, 개발자 도구를 모두 제공한다. 이름은 여러 브라우저에서
  통하는 일반 명칭을 쓴다.
- Ctrl+T가 명령 바를 열지 새 탭 페이지를 열지 사용자가 고른다.
- Ember는 스페이스 구성과 고정 탭을 동기화한다. 열린 탭 동기화는 이후에 정한다.
- 왼쪽 열은 Appbar라고 부른다. Sidebar는 오른쪽의 확장 프로그램 영역이다. 레일은 자기 폭만큼 자리를 차지하고,
  열린 확장 패널은 웹 페이지 폭을 줄이지 않고 페이지 위에 떠서 보인다.
- 화면의 기준은 `rivet/runtime/windows/demo/rivet-shell-demo.html`이다.

### D11. 모든 Rivet UI는 브라우저 창 표면의 일부다

Appbar에 적용한 원칙을 Rivet의 모든 UI 컴포넌트에 적용한다. 메뉴, 명령 바,
Sidebar, 링크 미리보기, 분할 보기 경계, 알림이 모두 대상이다.

- 컴포넌트는 브라우저 창의 DirectComposition visual로 그린다. 별도 최상위 창, 소유 팝업, 자식 창을 만들지 않는다.
  Windows가 브라우저와 한 창으로 합성하므로 이동, 크기 변경, 최대화, 스냅, DPI 변경, 애니메이션을 따로 맞출
  필요가 없다.
- 위치와 크기는 브라우저가 실제로 배치한 배율과 창 크기에서 매번 다시 계산한다. 화면 좌표를 한 번 잡아 두고
  쓰지 않는다.
- 입력은 Rivet이 서브클래싱한 브라우저 창에서 받는다. 마우스는 hit test로, 키보드는 편집 중에 브라우저 창의
  키 메시지로 받는다. 포커스와 활성 상태는 브라우저 창에 그대로 둔다.
- 글자 입력은 새로 구현하지 않는다. 주소 줄의 제안, 보안 표시, 페이지 정보는 Chromium 함수에서 얻는다(D12).
  주소 줄과 Rivet 고유 입력(명령 바, Appbar 검색 등)은
  Windows의 창 없는 텍스트 엔진(windowless RichEdit, `ITextServices`)을 쓴다. Rivet은 브라우저 창의 키 메시지를
  넘기고 결과를 visual에 그리며, 편집 동작, IME, 클립보드, 실행 취소는 엔진이 처리한다.
- 기능은 브라우저의 것을 쓴다. 주소 열기, 이동 상태, 주소 읽기처럼 브라우저가 이미 가진 동작은 브라우저 함수를
  부르고, Rivet은 표시와 입력만 맡는다.
- 브라우저 화면을 덮어 같은 모양을 흉내 내지 않는다. 브라우저 요소의 모양이 다르면 브라우저 레이아웃이나 그리기
  경로에서 바꾼다.

예외가 필요하면 먼저 이 결정을 바꾼다.

### D11-기각. 검토하고 버린 UI 방식

| 방식 | 버린 이유 |
|---|---|
| 주소 입력을 위해 상단 줄 위에 소유 팝업 EDIT 창 띄우기 | 별도 창이라 창 이동, 크기 변경, DPI 변경 때 위치가 어긋난다. 포커스가 팝업으로 넘어가 브라우저 창이 비활성으로 그려지고, 포커스를 되찾는 우회 처리가 필요하다 |
| 키 입력, IME, 편집 동작을 Rivet이 직접 구현하기 | 단어 이동, 붙여넣기, 실행 취소, 입력기별 동작, 스크린 리더 지원까지 범위가 넓고 이미 검증된 구현을 다시 만드는 일이다 |
| 브라우저 창의 자식 창으로 입력 컨트롤 두기 | 최상위 DirectComposition visual 아래에 깔려 보이지 않고, 브라우저의 포커스 관리와 충돌한다 |

### D12. Rivet은 app window 위에 자기 상단 줄과 분할 보기를 만든다

소유자 결정(2026-11-04): Rivet은 Chromium만 쓰는 app window 체계로 다시 구현한다. 이전 결정(브라우저 툴바를 덮어써서
상단 줄을 만든다)은 이 결정으로 바뀐다.

- Rivet 창은 브라우저의 app window 모드(`--app`)로 연다. 회사가 바꾼 툴바와 UI는 이 창에 나오지 않으므로 상관없다.
- 상단 줄(뒤로, 앞으로, 새로 고침, 주소 줄)은 app window에 없으므로 Rivet이 브라우저 창 표면에 직접 그린다(D11).
  주소 줄의 IME, 제안, 보안 표시, 페이지 정보는 Rivet이 그리되 내용과 동작은 Chromium 함수에서 얻는다.
- 비밀번호, 패스키, 권한은 브라우저 소유로 남고 동작해야 한다. 그 말풍선은 Rivet 창에 붙어 보여야 한다.
- 분할 보기와 Sidebar 페이지는 Rivet이 BrowserView의 `views::View`에 더한 두 번째 `ContentsWebView`(Chromium
  `views::WebView`)에 보여 준다. 웹뷰가 아니라 Chromium 자신의 페이지 뷰다.
- 탭은 Rivet이 소유한다. Chromium `TabStripModel` 함수로 탭을 app window에 옮기고, 분할된 페이지가 클릭 때문에 주
  페이지 뷰로 돌아가지 않게 한다.
- Rivet은 Chromium 코드만 호출하거나 덮어쓴다. 회사 코드(Naver, Samsung, Microsoft, Brave 함수)는 호출하지 않는다.
  지원 브라우저는 모든 기능이 같다(D8).
- 주소는 빌드마다 다르다. 서명된 지원 빌드 표의 행으로 적용하고, 원래 바이트를 확인한 뒤에만 덮어쓴다(D7).

### D12-기각. 검토하고 버린 상단 줄과 분할 방식

| 방식 | 버린 이유 |
|---|---|
| 일반 창의 브라우저 툴바를 덮어쓰기 | 회사마다 UI가 달라 빌드마다 약 371개 값을 찾아야 한다 |
| 회사의 분할 기능 호출 | 회사 코드를 부르므로 Chromium 코드만 쓴다는 결정과 맞지 않는다 |
| app window 안에서 Chromium 탭 분할 쓰기 | 일부 브라우저의 창은 Chromium 탭 분할을 한 페이지로만 보여 준다 |
| 주소 없는 `WM_COMMAND` 경로 | 탭을 원하는 창과 자리에 놓을 수 없다 |
| 웹뷰로 상단 줄이나 페이지 그리기 | 페이지 렌더링에 웹뷰를 쓰지 않는다는 조건과 맞지 않는다 |

### D13. Rivet이 만드는 파일은 한 뿌리 아래 정해진 자리에 둔다

소유자 결정(2026-11-04): Rivet이 실행 중에 만드는 모든 파일은 `%LOCALAPPDATA%\Rivet\` 한 곳 아래, 종류마다 정해진 폴더에
둔다. OS 임시 폴더는 조심해서 쓴다.

- `config`: 저장한 설정(`setup.json`)과 시험자가 손으로 놓는 디버그 스위치(`config\debug`).
- `profiles`: Rivet이 만든 브라우저 프로필. 안의 내용은 브라우저 소유다.
- `state`: 세션 기록(`sessions.json`)과 프로필마다의 공간(`spaces`).
- `cache`: 다시 받거나 다시 만들 수 있는 것. 서명된 빌드 표(`builds`), 보관 브라우저(`browsers`), 짧게 쓰는 파일(`scratch`).
- `logs`: 켰을 때만 쓰는 추적 기록.
- 설치 폴더에는 아무것도 쓰지 않는다. 사용자 계정이 쓸 수 없고, 업데이트가 폴더를 바꾸기 때문이다.
- 두 번째 뿌리(`%LOCALAPPDATA%\LogitAI\Rivet`)는 없앤다.
- 보관 한도: 지워진 프로필의 공간 파일은 지운다. 읽지 못해 옆에 둔 공간 파일은 30일, 로그는 마지막으로 쓴 지 14일 뒤 지운다.
  로그 파일 하나는 4 MiB에서 `.old` 하나로 돌린다. 보관 브라우저는 브라우저마다 최신 검증 빌드 2개만 두고, 끝나지 않은
  복사본은 하루 뒤 지운다. `scratch`의 파일은 하루 뒤 지운다.
- 이전 자리의 파일은 시작할 때 한 번 옮긴다. 같은 볼륨 안의 이름 바꾸기만 쓰고 복사하지 않는다. 파일이 열려 있어 옮기지
  못하면 그대로 두고 다음 시작에 다시 한다. 프로필 안은 열지 않는다.
- 제품 코드는 OS 임시 폴더를 쓰지 않는다. Windows가 임시 파일을 요구하는 경우에만 Rivet 이름의 하위 폴더를 쓰고 지운다.
  시험은 crate의 target 폴더(또는 `CARGO_TARGET_TMPDIR`) 아래 시험마다의 폴더를 쓰고 지운다.
- 경로는 한 모듈(`rivet-core`의 `paths`)만 만든다. 다른 파일이 `LOCALAPPDATA`를 읽거나 `temp_dir()`을 부르면 검사가 실패한다.
- 설치 도구는 `%LOCALAPPDATA%`에 아무것도 만들거나 지우지 않는다. 제거해도 프로필과 데이터는 남는다. 묻지 않고 프로필을
  지우지 않는다.

### D13-기각. 검토하고 버린 파일 자리

| 방식 | 버린 이유 |
|---|---|
| 추적 로그와 스위치를 설치 폴더에 두기 | 사용자 계정이 쓸 수 없고, 업데이트가 폴더를 바꾸면 사라진다 |
| 시험 파일을 OS 임시 폴더에 두기 | 다른 프로그램과 함께 쓰는 폴더라 남은 파일이 쌓이고 정리되지 않는다 |
| 이전 자리의 보관 브라우저를 복사해 옮기기 | 3.8 GB를 복사하는 동안 디스크와 시간을 쓰고, 이름 바꾸기로 충분하다 |
| 프로필이 없을 때 회사 기본 프로필(`Google\Chrome\User Data`)을 읽기 | 사람의 브라우저 데이터이고, Rivet 세션은 늘 자기 프로필로 시작한다 |

### D14. 비밀번호와 패스키는 사용자가 고른 제공처가 맡는다

소유자 결정(2026-11-04): Rivet은 비밀번호와 패스키를 직접 저장하거나 옮기지 않는다. 사용자가 고른 제공처가 맡는다.

- Windows의 Rivet: 브라우저(Chromium)의 비밀번호 관리자 또는 운영체제의 제공처 중에서 고른다. Windows에는 다른 앱의
  비밀번호 칸을 채우는 시스템 구조가 없어, 운영체제 제공처는 사실상 패스키(Windows Hello와 연결된 패스키 관리자)다.
- Android의 Rivet(Chromium Desktop Android 빌드의 결과물을 불러 쓰는 독립 앱): 시스템에 등록된 제공처(Google 비밀번호
  관리자, Samsung Pass, 그 밖의 자동완성 서비스와 Credential Manager 제공처) 중에서 고른다. 다른 앱의 저장소는 읽지 않는다.
- 시스템 제공처로 내놓지 않는 관리자의 비밀번호는 Rivet이 가져오지 않는다. 사용자가 직접 옮길 수 있게 안내만 한다.
  2026-11-04 Galaxy S21(Android 15) 조회에서 Whale은 제공처가 아니었다.
- Ember는 원래 브라우저 데이터를 Ember 메인 서버에 둔다. 이 결정은 Rivet의 브라우저에만 해당한다.

### D14-기각. 검토하고 버린 비밀번호 방식

| 방식 | 버린 이유 |
|---|---|
| 다른 브라우저의 비밀번호 저장소를 읽어 오기 | Android는 앱 저장소를 격리하고, 비밀번호를 복사하지 않는 원칙(NFR-2)에 어긋난다 |
| Android 앱 안의 Chromium 관리자에만 저장하기 | 비밀번호가 Rivet 앱에 갇혀 다른 앱과 브라우저에서 쓸 수 없다 |
| 자체 빌드 Chromium에서 Google 계정 동기화 쓰기 | Google이 2021년부터 자체 빌드의 Chrome 동기화 API를 막았다 |
